# Bhava handoff

Bhava is a white-label platform for Instagram and Facebook commerce. Many businesses run on one codebase and one database, and every business is onboarded the same way: there is never code for one client.

The requirements (PRD) and build plan live outside this repo, because the repo is public. Work happens on `bhava/build`.

## Rules that never bend

- Every business-owned row has `tenant_id`; every business repo calls `tenantId()` and refuses to run without one. New tables get `tenant_id` and composite foreign keys.
- Everything a seller uses is Bhava-branded; everything a buyer sees is the seller's brand. No Bhava text in DMs.
- Nothing sends to Instagram, Facebook or WhatsApp except through the compliance gate once it exists.
- No usernames, message text or phone numbers in logs. Money is integer paise.
- DM links are direct: no Bhava redirect or shortener.

## Where things are

## Interfaces other work builds on

**Modules** (`src/modules/index.js`): an object with a `name` and any of `repos`, `beforeTenant`, `routes`, `platformRoutes`, `api`, `jobs`. List it in `MODULES`; `createApp`, `createRepos` and `registerJobs` do the rest.

**Seller API** (`src/contracts/api`): `routes` is the table of every `/api/v1` route, with its method, path, `access`, zod schemas for input and output, and success status. The router in `src/modules/api-v1` is built from it. A module answers routes with `api(ctx)` returning `{ 'products.get': async ({ params, query, body, file, user, req, res }) => result }`. Returning null is a 404; throw `ApiError(code, message)` to refuse, and a repo's `ValidationError` becomes a 400. A route nobody answers is a 501. Results are parsed through the response schema, so a field not in the schema never leaves the server. Every failure is `{ error, code, fields?, requestId? }`. Lists take `cursor` and `limit` and return `{ items, nextCursor }`. A new route goes in the contract first, with its method added to `shared/api-client/index.js`; a test keeps the two in step.

**Access** (`src/contracts/api/access.js`): each route names `PUBLIC`, `SIGNED_IN`, `OWNER_ONLY`, `MANAGERS` or `staffWith(permission)`. Staff reach a route only through its named permission (`users.permissions`, set with `repos.users.setPermissions(id, list)` or `npm run role -- <phone> staff orders,catalog`). Refusals and lookups that find nothing are logged with ids only. There is no Team screen yet.

**One person, several businesses.** `X-Tenant-Id` on any `/api/v1` call asks to work in that business. It is checked against `memberships` on every call: not a member, or no such business, is a 403 with code `forbidden`, and a member becomes that person's account there, with that account's role and permissions. `GET /api/v1/auth/businesses` lists them for a switcher. A row in `memberships` is written only when the person proves both accounts are theirs, which with passwords means the same password opens both (`users.verify`). Never match on phone alone: an owner can type anyone's number onto a staff account. When one-time codes arrive (PRD 5.11), a verified phone becomes the proof.

**Row-level security.** Every table with a `tenant_id` has a policy (`tenant_fence`) that shows a transaction only the rows of `app.tenant_id`. `db.query`, `db.exec` and `db.tx` inside `withTenant()` run as the role `bhava_app` (not the owner, no superuser, no bypass) with `app.tenant_id` set for that transaction, so a query that forgets its `WHERE` still sees one business. Keep writing `WHERE tenant_id = $1` as well: the fence is the second lock, and the indexes need it. Through `db.platform.query/exec/tx` work runs as the owner with no fence. Use `db.platform` only for what is about no single business or has to look across them: routing a host or webhook to its business, the job queue, retention, the Platform Console. `repos.tenants` and `repos.platformUsers` already do.

**Two database logins.** Production sets two connections. `DATABASE_URL` logs in as `bhava_app` itself (or a login that is a member of it and of nothing else): no superuser, no bypass, owns nothing, cannot change role. Every `db.query/exec/tx` runs on it, so nothing a query injects can step up to the owner, and `RESET ROLE` leaves it where it was. `DATABASE_OWNER_URL` logs in as the owner of the tables and is used for migrations, backup and restore (`ownerDatabaseUrl(config)`), and `db.platform`, on a smaller pool of its own. The first start makes the app login with the password in `DATABASE_URL` (`ensureAppLogin`), and every start refuses a `DATABASE_URL` whose login could get around the fence (`assertRestrictedLogin`). `db.logins` is 2.

With only `DATABASE_URL` set (`db.logins` is 1; tests, PGlite, older setups) that one login is the owner, and it steps down to `bhava_app` with `SET LOCAL ROLE` for each transaction inside `withTenant()`. Production logs `db.single_login` once at start. The two modes differ in one place: `db.query` outside `withTenant()` and not through `db.platform` runs as the owner with one login, and as `bhava_app` with no business, seeing no business rows, with two. So anything that looks across businesses must say `db.platform`; do not rely on being outside `withTenant()`. `openTestDb({ logins: 2 })`, `setup({ logins: 2 })` and `startApp({ logins: 2 })` in `test/helpers.js` give a test the two-login database when `TEST_DATABASE_URL` is set (`test/p4/db-login`).

What the fence does not do: the business is still named by `app.tenant_id`, a setting the app login can write. It stops a forgotten `WHERE` and a query stepping up to the owner; it does not make injected SQL harmless, so every value still goes in as a parameter.

A new table, in a migration numbered for your phase:

```sql
CREATE TABLE widgets (
  id         serial PRIMARY KEY,
  tenant_id  integer NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  product_id integer NOT NULL,
  UNIQUE (tenant_id, id),                                                   -- so other tables can link to this one
  FOREIGN KEY (tenant_id, product_id) REFERENCES products(tenant_id, id) ON DELETE CASCADE
);
CREATE INDEX widgets_product_idx ON widgets (tenant_id, product_id);
SELECT fence_tenant_table('widgets');                                       -- policy, grants, and its serial id
```

The foreign key carries `tenant_id`, so the database refuses a link to another business's row. For an insert-only table use `fence_tenant_table('widget_log', 'SELECT, INSERT')`. A table shared by every business with no `tenant_id`, such as `plans`, needs `GRANT SELECT ON x TO bhava_app`; a platform-only table needs no grant at all. With no grant, business code gets "permission denied", which is the point. A business may read only its own row of `tenants` and change only `next_order_number`; anything else on that table goes through `repos.tenants`. Backups keep privileges, and a restore creates the role first.

**Audit log** (`repos.audit`): `record({ actor, action, target, details })` adds a row for the current business, and `writeAudit(t, entry)` from `src/modules/audit` does it inside an open transaction, so the change and its row land together. `actor` is an id such as `user:12`. Details never hold secrets, tokens or usernames: mask first. Owners read it at `GET /api/v1/audit-log`.

**Payment keys** (`repos.gatewayKeys`): `save('razorpay', { keyId, keySecret }, actor)` encrypts the secret and writes the masked audit row in one transaction; `get('razorpay')` returns them decrypted, or null.

**Seller console** (`console`): at `/admin` on each business's address, whatever `ADMIN_UI` says; the old server-rendered pages are gone. Build it with `npm run build:console`. A feature is `console/src/features/<name>/index.jsx` and registers itself: see `console/src/features/index.js`. Components and tokens are in `console/src/design`; the API client is `api` from `console/src/lib/api`. The console signs in with a cookie session (`transport: 'cookie'`), and the client sends the CSRF token for you.

**Brand kit** (`repos.brandKit`): `get()` returns `{ preset, presetName, logoUrl, logoDarkUrl, faviconUrl, colors, headingFont, bodyFont, publicReplyVariants }`; `save(partial)` validates colours, the 4.5:1 primary and on_primary contrast, the font allow-list and the public replies (none, or 5 to 10 different ones of up to 150 characters, with no link, phone number or price); `presets()` lists the looks. Presets are rows in `theme_presets`, with the codes `utsav`, `dewdrop`, `tadka`, `gadget-galli` and `mitti`. Buyer pages use `buyerSettings(repos)` from `src/modules/brand`, and `brandCss` and `brandFontsHref` from its `theme.js`.

**Entitlements** (`repos.entitlements`): `can(feature)` is true or false; `limit(feature)` is a number, `Infinity` for no limit, or 0 when not included; `setOverride(feature, { enabled, limit })`, `clearOverride(feature)`. Plans are in `plan_features`, per-business changes in `tenant_features`. A `tenant_features` row replaces the plan's row for that feature. Features seeded: `automations`, `dms.monthly`, `insights.days`, `reel.products`, `triggers.comment`, `triggers.story_dm`, `links.two_tap`, `links.one_tap`, `store.checkout`, `app.android`, `app.ios` and others in migration 004.

**Roles.** Business users are `owner`, `manager`, `staff` or `customer`; `auth.requireRole(...roles)` guards a route. A business's status is `onboarding`, `active`, `paused`, `suspended` or `closed` (`killed` is also allowed). Bhava's team are `platform_users` (`super_admin`, `support`): they sign in with `POST /login` on the platform host (`PLATFORM_HOST`, by default `admin.<PLATFORM_DOMAIN>`) and `requirePlatformRole(...roles)` from `src/auth.js` guards their routes. Add one with `npm run platform-user`.

**Instagram** (`src/instagram.js`): `createInstagram(config)` gives a client whose calls take the account first, for example `getMedia(account, id)`, where `account` is `{ igUserId, token }` from `repos.igAccounts` (`get(igUserId)`, `current()`, `setToken(igUserId, token)`). `forAccount(client, account)` binds one account, and `await forBusiness(client, repos, igUserId?)` binds the current business's. Tokens are encrypted with `DATA_KEY`. It runs on the Meta adapter, so it has the same timeouts and host rules.

**Meta adapter** (`src/adapters/meta`, `ctx.meta`): `meta.client.forAccount(account)` for reads and setup (media, stories, comments, a person's profile, `subscribe`, ice breakers), and `meta.login` for connecting: `authorizeUrl({ state, redirectUri })`, `connect({ code, redirectUri })`, `refresh(token)`. `META_LOGIN` chooses Instagram Login or Unified Login behind that one interface, and scopes always come back in Instagram Login's names. `meta.facebookLogin` connects Pages. Every call has a 10 s timeout, follows no redirect and keeps the token out of the URL. `GRAPH_BASE_URL` points everything at a simulator, which is refused when `NODE_ENV=production`, and any host that isn't Meta's throws `api.host_blocked`. A failure is a `MetaApiError` with `kind` (`token_invalid`, `throttled`, `validation`, ...), `delivery` (`none` when Meta's answer proves nothing was delivered, `unknown` when it may have been: never resend those), `status`, `code`, `subcode` and `usage`. Provider callbacks use `verifyHubSignature` and `verifySignedRequest`, which return false or null on bad input and never throw.

**Compliance** (`src/modules/compliance`, `ctx.compliance`): the only path to Meta for a message. `send(action)` sends now, `enqueue(action)` creates the `outbound_jobs` row for the worker, `check(action)` applies the rules with no side effects. `action` and the result are in `src/contracts/compliance.js`, with the reason codes and every limit. Meta's refusals come back as a result with an `outcome` and `reason`; `send` throws only on an invalid action or with no current business. Nothing else may call `meta.client.sender` or the `ig` send calls, and a test enforces that. `repos.compliance.subjectHash(channel, personId)` is the only form of a person's id the log, blocklist and caps hold. A rule that refuses an API call throws `ApiError(code, message, { reason })`, and `reason` appears in the error body. **Until the compliance track fills it in, this is a stub that validates, sends and logs and applies no rules.** A module's `beforeTenant` runs before the Phase 0 webhook routes in `src/server.js`, so registering `POST /webhook` there replaces them.

**Between Phase 1 tracks.** The tables are the shared surface: webhook intake writes `inbound_events`, `inbox_threads`, `inbox_messages` and `needs_human_items`; the automations track reads them and owns `automations` and its children. Shared pure functions have one home each: `matchesKeywords` in `src/modules/automations/match.js`, `checkContent` and `fillTemplate` in `src/modules/compliance/content.js`, `directLink` and `linkProblem` in `src/modules/links/rules.js`. Import them from there and keep the signatures. Tell the owner or ops with `repos.alerts.raise({ kind, message, severity, target, dedupeKey, audience })`; email and push read that table when they are built. Addresses Meta and Caddy call are `PROVIDER_PATHS` and their shapes in `src/contracts/api/provider.js`.

**Phase 1 modules**: `ig-connect`, `compliance`, `automations` (also testers, ice breakers, the inbox), `links`, `facebook`, `domains`. Each answers its routes in `src/contracts/api` with `notBuilt(...)` (a 501) until the real handler replaces that id. Platform Console routes are in `platformRoutes` in `src/contracts/api/platform.js`. `channel` is `instagram` or `facebook`, and a table that belongs to one account has `ig_user_id` and `fb_page_id`, exactly one of them set, each with its own composite key. `ctx.config.facebookPages` is the flag for Facebook. Test against `createMeta` from `tools/sim/meta`: Facebook's controls are listed in `tools/sim/meta/facebook.mjs`.

**Bearer sessions.** `POST /api/v1/auth/login` on a business's address, with `{ phone, password }` and no `transport`, returns a token. Afterwards `Authorization: Bearer <token>` sets the user and the business, before the web address is looked at, and CSRF does not apply. A bad token gets 401, and so does a good token sent to another business's own address (its custom domain or `<slug>.PLATFORM_DOMAIN`). An address that belongs to no business, or only falls back to `DEFAULT_TENANT`, takes any token. `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`. Access tokens and refresh rotation (PRD 10.2) are not built yet: a token lasts 30 days.

**Phase 2 contract** (PRD 7). Numbers, names and catalogues are in `src/contracts/analytics.js`; routes are `src/contracts/api/{insights,reach-guard,traffic,reports}.js`; each is answered with `notBuilt(...)` in `src/modules/{insights,reach-guard,traffic,reports}` until its handler replaces that id.

Every one renders with the shared layout in `src/views/buyer`: `loadBuyerLayout(repos)` gives the theme and business, `buyerPage({ theme, business, meta, main, headerEnd, footer })` the document, with `hero`, `ticker`, `section`, `productCard`, `tileStrip`, `trustRow`, `sealBadge`, `icon`, `notFoundPage` and `priceText` for its parts, and `sendBuyerPage(res, view, { page: { kind, ref } })` sends it and tells the traffic counter what it is (`res.locals.page`, read by the traffic module). The layout writes the seller's brand only; a test renders every preset and looks for the platform's name. Links go through `safeHref` and are direct; a product button carries `data-product`, which the traffic script now sends with an outbound or WhatsApp tap.
- *Policy (5.18).* `npm run policy-check` (also in CI) fails code that compares a business's id, slug or name with a fixed value, names a fixed `tenant_id` in SQL, or names a sample business.
- *Database driver.* bigint now reads as a number on `pg` too, as it already did on PGlite (a BigInt past 2^53), so the two drivers agree.

**Phase 4 contract** (PRD 9: the store). Requirements are `requirements/p4.json` (S-01 to S-104). Each track owns one folder under `src/modules` and edits nothing outside it: `storefront`, `cart`, `checkout`, `orders`, `inventory`, `coupons`, `shoppers`, `consent`, `payments`, `refunds`, `shipping`, `invoices`, `returns`, `reviews`, `wishlist`, `loyalty`, `order-alerts`, `abandoned-cart`, `shopify-sync`. Each folder's `index.js` says what it owns: its tables, its console routes (answered with `notBuilt(...)` until built), its buyer routes and the order events it listens to. A test (`test/p4/contract`) keeps every route with its module.

- *Money.* bigint paise everywhere. No route, console or buyer, takes an order amount: the server prices every line from the catalog and works out every total, and the buyer bodies in `src/contracts/store-routes.js` are strict, so a price or total in a request is refused. The rules (`orderTotal`, `taxInside`, `splitGst`, `financialYear`) and the limits (`STORE_LIMITS`) are in `src/contracts/orders.js`. The one amount a person types is a refund's, and the database holds refunds inside what was captured.
- *Orders (402).* `orders` and `order_items` grew in place. An order has `fulfilment_status` and `payment_status`, kept apart, and may be on hold (`hold_reason`). The Phase 0 `status` column stays and the database derives it, so every earlier reader (home numbers, traffic, the funnel) is unchanged; a confirmed order reads as `paid` there, cash on delivery included. `flow` is `manual` for a Phase 0 order (its `status` is written as before and the two new columns follow) and `checkout` for a Phase 4 one, which must obey the machine, must have lines that add up to its totals (checked at commit), and cannot have its totals, number or way of paying changed afterwards. `advance_paise` and `balance_paise` are as placed; the label's COD amount is the balance.
- *The state machine* (`src/modules/orders/state.js`). The only code that changes the status of an order, payment, refund, shipment or return: `changeOrder(t, id, { fulfilment?, payment?, actor, reason?, cancelReason?, set?, ifAllowed? })`, `holdOrder`, `releaseOrder`, `addOrderNote`, `changeRow(t, 'payments' | 'refunds' | 'shipments' | 'returns', id, to, { set?, ifAllowed? })`, and `setManualStatus` for Phase 0 orders. Each takes the open transaction. The moves and guards are data in `src/contracts/orders.js` (`TRANSITIONS`), the same rows are in `status_transitions`, and triggers refuse anything else, so SQL that goes round the file still cannot make a move that isn't allowed. `ifAllowed: true` is for provider events: a late or repeated one is skipped and reported, never thrown, and nothing moves backwards. The database writes the timeline (`order_status_history`) for every change; `actor` is an id such as `user:12` or `webhook:razorpay`.
- *Order events* (`src/modules/orders/events.js`, `ctx.orderEvents`). A trigger writes an outbox row (`order_events`, 403) in the same transaction as every change to an order, payment, refund, shipment or return, so no change commits without its event. The worker hands each to every listener at least once, in order per order, with backoff, and tells ops after 8 failed tries. Register in the module's `setup(ctx)`: `ctx.orderEvents.on('order.paid', 'invoices.issue', handler)`. Types are `ORDER_EVENTS`; an event is ids and statuses only. Listeners must be idempotent: every table one writes has a unique key for that (`stock_movements (reason, ref)`, `loyalty_ledger.entry_key`, `order_alerts (order, event, channel)`, `invoices` per order and per refund, `settlement_lines (kind, ref)`, `shopify_order_pushes` per order). A module adds its own events (`EMITTED_EVENTS`) with `ctx.orderEvents.emit(t, ...)`. After a commit, `ctx.orderEvents.kick()` delivers at once in that process; tests call `await app.ctx.orderEvents.settle()` (`startApp` now returns `ctx`). The traffic order link is one of these listeners (`traffic.order-link`): checkout stores `visitorIdFrom(req)` in `orders.visitor_id` and wraps nothing.
- *Module hooks.* `setup(ctx)` runs once in the app and once in the worker (listeners, the consent provider). `lastRoutes(app, ctx)` mounts after every module's routes: the storefront's pages and the store's 404. `ctx` gained `providers`, `shopperMessages` and `orderEvents`.
- *The Phase 0 store* moved out of `src/routes` (store.js and account.js are gone) into `legacy.js` in `storefront`, `checkout` and `shoppers`, behaving as before; `repos.orders` is `src/modules/orders/legacy.js`. A track replaces a page by mounting its own and removing the old one from its `legacy.js`. `POST /login` also signs sellers in: keep that.
- *Adapters* (`src/adapters/store.js`, `ctx.providers`): `razorpay` (one interface, `route` for Bhava's account with split settlement and `partner` for the seller's own by Partner OAuth; `forMode(mode)`, default from `PAYMENT_MODE`), `shiprocket` (managed or `forAccount(own)`), `shopify` (`forShop`), `whatsapp`, `email`. Every call has a 10 s timeout and no redirect; a base URL (`RAZORPAY_BASE_URL`, `SHIPROCKET_BASE_URL`, `SHOPIFY_BASE_URL`, `WHATSAPP_BASE_URL`, `EMAIL_BASE_URL`) points at a simulator, which is refused when `NODE_ENV=production`, and any other host that isn't the provider's throws at start. A failure is a `ProviderError` with `kind`, `retryable` and `delivery`: `unknown` means the provider may have acted, so the call is repeated only with its idempotency key.
- *Provider webhooks.* Paths and signature headers are `STORE_PROVIDER_PATHS` and `SIGNATURE_HEADERS`. Verify on the raw bytes (`verifyWebhook` of each adapter; a bad signature is 401 and nothing is stored), insert into `provider_webhook_events` (unique `(provider, scope, event_id)`, platform only) before answering 2xx, then work from the queue. A managed Razorpay event is routed by linked account and gateway order; one that names another business's order or account is stored, ignored and flagged `security`.
- *Messages to shoppers.* `ctx.shopperMessages.send(message)` is the only path to WhatsApp or email (`src/contracts/shopper-messages.js`): consent first (a login code needs none), marketing never between 9 pm and 9 am, an approved template, the seller's brand only, and never twice on a guess. Nothing else calls `sendTemplate` or the email adapter; a test keeps it so. There is no SMS, and no Instagram DM for a cart.
- *Consent* (`platform.consent`, `src/platform/consent.js`): `allows`, `analyticsAndAds`, `record`, `revoke`, `status`, `notice`. The consent module registers the provider in `setup(ctx)` with `ctx.platform.consent.use(...)`. Until it does, every question is answered no and every write throws `ConsentNotReadyError`.
- *Limits across instances.* `platform.rateLimit.hit(scope, subject, { limit, windowMs })` counts in Postgres and stores only a hash.
- *Tables (400 to 416).* Shoppers, sessions, one-time codes and addresses (400); carts (401); orders (402); events (403); payment settings, payments, provider webhook events, refunds, settlement lines (404); stock with reservations (405: `stock` and `reserved` on products and variants, and the database refuses a hold beyond what is on hand); coupons (406: `used_count <= max_uses` is a check); shipping (407: an AWB names one parcel anywhere); invoices (408: the database numbers them per business, kind and financial year with no gap; never insert with `ON CONFLICT` and never choose a number); WhatsApp accounts and templates, alert settings, order alerts, cart reminders (409); returns (410; proof files go to private storage, never `/media`); consent (411); reviews and wishlist (412); loyalty and referrals (413); Shopify sync (414); the shared shopper profile (415: no `tenant_id`, no grant, reached only through `db.platform`); plan features (416).
- *Simulators.* `tools/sim/razorpay`, `shiprocket`, `shopify` and `whatsapp` now send their webhooks: signed, with `duplicates`, held and flushed in another order, with a bad signature, on the controlled clock (`tools/sim/webhooks.mjs`; each file's header lists its controls). `tools/sim/email` is an HTTP mail API a test starts itself.
- *Buyer routes.* `STORE_ROUTES` lists every page and JSON call with its owner. JSON is under `/api/store`. The shared-profile consent screen is the one buyer page that may name the platform.
