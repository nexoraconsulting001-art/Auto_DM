# Bhava handoff

Bhava is a white-label platform for Instagram and Facebook commerce. Many businesses run on one codebase and one database, and every business is onboarded the same way: there is never code for one client.

The requirements (PRD) and build plan live outside this repo, because the repo is public. Work happens on `bhava/build`.

## Rules that never bend

- Every business-owned row has `tenant_id`; every business repo calls `tenantId()` and refuses to run without one. New tables get `tenant_id` and composite foreign keys.
- Everything a seller uses is Bhava-branded; everything a buyer sees is the seller's brand. No Bhava text in DMs.
- Nothing sends to Instagram, Facebook or WhatsApp except through the compliance gate once it exists.
- No usernames, message text or phone numbers in logs. Money is integer paise.
- DM links are direct: no Bhava redirect or shortener.

## Interfaces other work builds on

**Modules** (`src/modules/index.js`): an object with a `name` and any of `repos`, `beforeTenant`, `routes`, `platformRoutes`, `api`, `jobs`. List it in `MODULES`; `createApp`, `createRepos` and `registerJobs` do the rest.

**Seller API** (`src/contracts/api`): `routes` is the table of every `/api/v1` route, with its method, path, `access`, zod schemas for input and output, and success status. The router in `src/modules/api-v1` is built from it. A module answers routes with `api(ctx)` returning `{ 'products.get': async ({ params, query, body, file, user, req, res }) => result }`. Returning null is a 404; throw `ApiError(code, message)` to refuse, and a repo's `ValidationError` becomes a 400. A route nobody answers is a 501. Results are parsed through the response schema, so a field not in the schema never leaves the server. Every failure is `{ error, code, fields?, requestId? }`. Lists take `cursor` and `limit` and return `{ items, nextCursor }`. A new route goes in the contract first, with its method added to `shared/api-client/index.js`; a test keeps the two in step.

**Access** (`src/contracts/api/access.js`): each route names `PUBLIC`, `SIGNED_IN`, `OWNER_ONLY`, `MANAGERS` or `staffWith(permission)`. Staff reach a route only through its named permission (`users.permissions`, set with `repos.users.setPermissions(id, list)` or `npm run role -- <phone> staff orders,catalog`). Refusals and lookups that find nothing are logged with ids only. There is no Team screen yet.

**One person, several businesses.** `X-Tenant-Id` on any `/api/v1` call asks to work in that business. It is checked against `memberships` on every call: not a member, or no such business, is a 403 with code `forbidden`, and a member becomes that person's account there, with that account's role and permissions. `GET /api/v1/auth/businesses` lists them for a switcher. A row in `memberships` is written only when the person proves both accounts are theirs, which with passwords means the same password opens both (`users.verify`). Never match on phone alone: an owner can type anyone's number onto a staff account. Without passwords (Phase 5 contract below) a verified identity is the proof.

**Row-level security.** Every table with a `tenant_id` has a policy (`tenant_fence`) that shows a transaction only the rows of `app.tenant_id`. `db.query`, `db.exec` and `db.tx` inside `withTenant()` run as the role `bhava_app` (not the owner, no superuser, no bypass) with `app.tenant_id` set for that transaction, so a query that forgets its `WHERE` still sees one business. Keep writing `WHERE tenant_id = $1` as well: the fence is the second lock, and the indexes need it. Through `db.platform.query/exec/tx` work runs as the owner with no fence. Use `db.platform` only for what is about no single business or has to look across them: routing a host or webhook to its business, the job queue, retention, the Platform Console. `repos.tenants` and `repos.platformUsers` already do.

**Two database logins.** Production sets two connections. `DATABASE_URL` logs in as `bhava_app` itself (or a login that is a member of it and of nothing else): no superuser, no bypass, owns nothing, cannot change role. Every `db.query/exec/tx` runs on it, so nothing a query injects can step up to the owner, and `RESET ROLE` leaves it where it was. `DATABASE_OWNER_URL` logs in as the owner of the tables and is used for migrations, backup and restore (`ownerDatabaseUrl(config)`), and `db.platform`, on a smaller pool of its own. The first start makes the app login with the password in `DATABASE_URL` (`ensureAppLogin`), and every start refuses a `DATABASE_URL` whose login could get around the fence (`assertRestrictedLogin`). `db.logins` is 2.

With only `DATABASE_URL` set (`db.logins` is 1; tests, PGlite, older setups) that one login is the owner, and it steps down to `bhava_app` with `SET LOCAL ROLE` for each transaction inside `withTenant()`. Production logs `db.single_login` once at start. The two modes differ in one place: `db.query` outside `withTenant()` and not through `db.platform` runs as the owner with one login, and as `bhava_app` with no business, seeing no business rows, with two. So anything that looks across businesses must say `db.platform`; do not rely on being outside `withTenant()`. `openTestDb({ logins: 2 })`, `setup({ logins: 2 })` and `startApp({ logins: 2 })` in `test/helpers.js` give a test the two-login database when `TEST_DATABASE_URL` is set (`test/p4/db-login`).

What the fence does not do: the business is still named by `app.tenant_id`, a setting the app login can write. It stops a forgotten `WHERE` and a query stepping up to the owner; it does not make injected SQL harmless, so every value still goes in as a parameter.

A new table, in a migration numbered for your phase:

```sql
CREATE TABLE widgets (
  id         serial PRIMARY KEY,
  tenant_id  integer NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  product_id integer NOT NULL,
  UNIQUE (tenant_id, id),                                                   -- so other tables can link to this one
  FOREIGN KEY (tenant_id, product_id) REFERENCES products(tenant_id, id) ON DELETE CASCADE
);
CREATE INDEX widgets_product_idx ON widgets (tenant_id, product_id);
SELECT fence_tenant_table('widgets');                                       -- policy, grants, and its serial id
```

The foreign key carries `tenant_id`, so the database refuses a link to another business's row. For an insert-only table use `fence_tenant_table('widget_log', 'SELECT, INSERT')`. A table shared by every business with no `tenant_id`, such as `plans`, needs `GRANT SELECT ON x TO bhava_app`; a platform-only table needs no grant at all. With no grant, business code gets "permission denied", which is the point. A business may read only its own row of `tenants` and change only `next_order_number`; anything else on that table goes through `repos.tenants`. Backups keep privileges, and a restore creates the role first.

**Audit log** (`repos.audit`): `record({ actor, action, target, details })` adds a row for the current business, and `writeAudit(t, entry)` from `src/modules/audit` does it inside an open transaction, so the change and its row land together. `actor` is an id such as `user:12`. Details never hold secrets, tokens or usernames: mask first. Owners read it at `GET /api/v1/audit-log`.

**Payment keys** (`repos.gatewayKeys`): `save('razorpay', { keyId, keySecret }, actor)` encrypts the secret and writes the masked audit row in one transaction; `get('razorpay')` returns them decrypted, or null.

**Seller console** (`console`): at `/admin` on each business's address, whatever `ADMIN_UI` says; the old server-rendered pages are gone. Build it with `npm run build:console`. A feature is `console/src/features/<name>/index.jsx` and registers itself: see `console/src/features/index.js`. Components and tokens are in `console/src/design`; the API client is `api` from `console/src/lib/api`. The console signs in with a cookie session (`transport: 'cookie'`), and the client sends the CSRF token for you.

**Brand kit** (`repos.brandKit`): `get()` returns `{ preset, presetName, logoUrl, logoDarkUrl, faviconUrl, colors, headingFont, bodyFont, publicReplyVariants }`; `save(partial)` validates colours, the 4.5:1 primary and on_primary contrast, the font allow-list and the public replies (none, or 5 to 10 different ones of up to 150 characters, with no link, phone number or price); `presets()` lists the looks. Presets are rows in `theme_presets`, with the codes `utsav`, `dewdrop`, `tadka`, `gadget-galli` and `mitti`. Buyer pages use `buyerSettings(repos)` from `src/modules/brand`, and `brandCss` and `brandFontsHref` from its `theme.js`.

**Entitlements** (`repos.entitlements`): `can(feature)` is true or false; `limit(feature)` is a number, `Infinity` for no limit, or 0 when not included; `setOverride(feature, { enabled, limit })`, `clearOverride(feature)`. Plans are in `plan_features`, per-business changes in `tenant_features`. A `tenant_features` row replaces the plan's row for that feature. From Phase 7 the `/api/v1` router asks it for every route that names `feature` or `limit` in the route table (see the Phase 7 contract), `lowestPlan(features, { moreThan? })` answers the lowest plan that includes one (the ladder is `plans.rank`), and `all()` is what `billing.features` returns. Features seeded: `automations`, `dms.monthly`, `insights.days`, `reel.products`, `triggers.comment`, `triggers.story_dm`, `links.two_tap`, `links.one_tap`, `store.checkout`, `app.android`, `app.ios` and others in migration 004.

**Roles.** Business users are `owner`, `manager`, `staff` or `customer`; `auth.requireRole(...roles)` guards a route. A business's status is `onboarding`, `active`, `paused`, `suspended` or `closed` (`killed` is also allowed). Bhava's team are `platform_users` (`super_admin`, `support`, `onboarding`, `service_operator`: `PLATFORM_ROLES` in `src/contracts/api/access.js`), on the platform host (`PLATFORM_HOST`, by default `admin.<PLATFORM_DOMAIN>`); `requirePlatformRole(...roles)` from `src/auth.js` guards their routes. They sign in with an emailed code plus TOTP (the Phase 7 ops contract below); `POST /login` with a password answers only while `PASSWORD_LOGIN` is on. Add one with `npm run platform-user`.

**Instagram** (`src/instagram.js`): `createInstagram(config)` gives a client whose calls take the account first, for example `getMedia(account, id)`, where `account` is `{ igUserId, token }` from `repos.igAccounts` (`get(igUserId)`, `current()`, `setToken(igUserId, token)`). `forAccount(client, account)` binds one account, and `await forBusiness(client, repos, igUserId?)` binds the current business's. Tokens are encrypted with `DATA_KEY`. It runs on the Meta adapter, so it has the same timeouts and host rules.

**Meta adapter** (`src/adapters/meta`, `ctx.meta`): `meta.client.forAccount(account)` for reads and setup (media, stories, comments, a person's profile, `subscribe`, ice breakers), and `meta.login` for connecting: `authorizeUrl({ state, redirectUri })`, `connect({ code, redirectUri })`, `refresh(token)`. `META_LOGIN` chooses Instagram Login or Unified Login behind that one interface, and scopes always come back in Instagram Login's names. `meta.facebookLogin` connects Pages. Every call has a 10 s timeout, follows no redirect and keeps the token out of the URL. `GRAPH_BASE_URL` points everything at a simulator, which is refused when `NODE_ENV=production`, and any host that isn't Meta's throws `api.host_blocked`. A failure is a `MetaApiError` with `kind` (`token_invalid`, `throttled`, `validation`, ...), `delivery` (`none` when Meta's answer proves nothing was delivered, `unknown` when it may have been: never resend those), `status`, `code`, `subcode` and `usage`. Provider callbacks use `verifyHubSignature` and `verifySignedRequest`, which return false or null on bad input and never throw.

**Compliance** (`src/modules/compliance`, `ctx.compliance`): the only path to Meta for a message. `send(action)` sends now, `enqueue(action)` creates the `outbound_jobs` row for the worker, `check(action)` applies the rules with no side effects. `action` and the result are in `src/contracts/compliance.js`, with the reason codes and every limit. Meta's refusals come back as a result with an `outcome` and `reason`; `send` throws only on an invalid action or with no current business. Nothing else may call `meta.client.sender` or the `ig` send calls, and a test enforces that. `repos.compliance.subjectHash(channel, personId)` is the only form of a person's id the log, blocklist and caps hold. A rule that refuses an API call throws `ApiError(code, message, { reason })`, and `reason` appears in the error body. Metering hooks in from outside (Phase 7): `useQuota({ hasDmsLeft })`, `onAccepted(fn)` and `releaseDmLimit()`, described in the Phase 7 contract. **Until the compliance track fills it in, this is a stub that validates, sends and logs and applies no rules.** A module's `beforeTenant` runs before the Phase 0 webhook routes in `src/server.js`, so registering `POST /webhook` there replaces them.

**Between Phase 1 tracks.** The tables are the shared surface: webhook intake writes `inbound_events`, `inbox_threads`, `inbox_messages` and `needs_human_items`; the automations track reads them and owns `automations` and its children. Shared pure functions have one home each: `matchesKeywords` in `src/modules/automations/match.js`, `checkContent` and `fillTemplate` in `src/modules/compliance/content.js`, `directLink` and `linkProblem` in `src/modules/links/rules.js`. Import them from there and keep the signatures. Tell the owner or ops with `repos.alerts.raise({ kind, message, severity, target, dedupeKey, audience })`; email and push read that table when they are built. Addresses Meta and Caddy call are `PROVIDER_PATHS` and their shapes in `src/contracts/api/provider.js`.

**Phase 1 modules**: `ig-connect`, `compliance`, `automations` (also testers, ice breakers, the inbox), `links`, `facebook`, `domains`. Each answers its routes in `src/contracts/api` with `notBuilt(...)` (a 501) until the real handler replaces that id. Platform Console routes are in `platformRoutes` in `src/contracts/api/platform.js`. `channel` is `instagram` or `facebook`, and a table that belongs to one account has `ig_user_id` and `fb_page_id`, exactly one of them set, each with its own composite key. `ctx.config.facebookPages` is the flag for Facebook. Test against `createMeta` from `tools/sim/meta`: Facebook's controls are listed in `tools/sim/meta/facebook.mjs`.

**Bearer sessions.** `POST /api/v1/auth/login` on a business's address, with `{ phone, password }` and no `transport`, returns a token. Afterwards `Authorization: Bearer <token>` sets the user and the business, before the web address is looked at, and CSRF does not apply. A bad token gets 401, and so does a good token sent to another business's own address (its custom domain or `<slug>.PLATFORM_DOMAIN`). An address that belongs to no business, or only falls back to `DEFAULT_TENANT`, takes any token. `GET /api/v1/auth/me`, `POST /api/v1/auth/logout`. This 30-day token works only while `PASSWORD_LOGIN` is on; access tokens and refresh rotation (PRD 10.2) are in the Phase 5 contract below.

**Phase 2 contract** (PRD 7). Numbers, names and catalogues are in `src/contracts/analytics.js`; routes are `src/contracts/api/{insights,reach-guard,traffic,reports}.js`; each is answered with `notBuilt(...)` in `src/modules/{insights,reach-guard,traffic,reports}` until its handler replaces that id.

- *Insights calls.* `meta.client.insightsFor(account, compliance.insightsGuard(channel, accountId))`: `accountDay`, `demographics`, `onlineFollowers`, `followers`, `mediaPage`, `storiesPage`, `mediaInsights`, `storyInsights`. The guard is required: it applies 4.3's call classes and pauses to every call and feeds usage and 80002 back to the rate state. A paused call throws `InsightsDeferredError` (try later); `isInsightsDenied(err)` means Permission needed. Results carry `status`: `ok`, `gone`, `expired` or `below_threshold`. Meta's metric names are `META_METRICS`. No request may contain `impressions`.
- *Rollups.* `platform.analytics.rollups`: `write`, `rebuild`, `clear`, `read`, `purgeExpired`, on the stores in `ROLLUP_STORES` (see `src/platform/analytics-rollups.js`). Nothing else touches `traffic_sessions`, `traffic_daily`, `traffic_items_daily`, `funnel_daily`, `meta_account_daily` or `meta_content_daily`, so a separate analytics database can take over without changing a caller.

Reach Guard re-asserts with `enter` at each evaluation. It changes the rate state the gate reads, and sends nothing. The override is the existing `compliance.slowModeOverride`.

To reach every buyer page, including ones later phases add, the traffic module's `routes(app, ctx)` middleware wraps `res.send` for HTML, adds the script and tags, and sets the page's CSP from `TAG_HOSTS`; no view has to change.

Like the email simulator, a test starts it itself.
